# JS D&D Campaign: Design

Date: 2026-11-07
Status: draft for approval. Nothing has been built or created on GitHub yet.
Repo: https://github.com/yamnyk/_JS-dnd.git (public, intended to be open source)

How to read this document: statements marked **[Gogi]** were said or confirmed by the owner. Statements marked **[My call]** are decisions I made and the owner has not seen. Statements marked **[My guess]** are inferences waiting for a yes or no. Statements marked **[Unchecked]** come from my memory and need verification before anyone relies on them.

---

## 1. Intent

A D&D-style adventure played in the terminal, where the player's own AI model is the Dungeon Master. Every quest is a real JS task: the player writes code in a file, and that code has to behave a certain way for the story to move on. The owner believes this is the first campaign of its kind.

**Why it exists [Gogi]:** curious beginners are tired of boring, gamified online tests. They like D&D and adventure, and they should learn by playing, not by clicking through quizzes.

**Success [Gogi]:** a player who finishes the campaign has working JS fundamentals up to async: the event loop, timeouts, and fetch. The number of 5hr sessions it takes does not matter. What matters is that the player goes through every quest and learns.

## 2. Audience

JS beginners who want to learn programming, who enjoy D&D, and who love adventures. No D&D mastering knowledge is assumed on the builder's side either: the owner has none, so D&D rules should follow the standard, widely known ruleset wherever a rule is needed.

## 3. Goals, non-goals, anti-goals

**Goals**
- A complete, playable campaign that teaches the full curriculum in section 5.
- Each player gets a unique world, generated by the Master.
- Gameplay burns as few tokens as possible, so a player gets more play out of one 5hr Claude usage window.
- Setup is one script, with no Docker and no manual dependency hunting.

**Non-goals (for now)**
- Gemini, Grok, and local-model support. Claude only at first, Gemini next, the rest later [Gogi].
- Combat as a full code-driven system. Only special moves get a JS problem; ordinary combat is D&D rules [Gogi].
- The digital certificate. The owner wants one but needs a link to some resource and will figure it out later [Gogi].
- Multiple heroes or worlds per install in the MVP [Gogi, accepted my recommendation].

**Anti-goals: what makes this a failure even if every feature works [Gogi]**
- Sloppy AI language while playing.
- Tasks that are too easy.

## 4. Constraints

- Claude Code is the first host. The play UI uses its built-in choice prompts [Gogi].
- Per the tool spec I have, a choice prompt takes 1 to 4 questions with 2 to 4 options each, plus a custom-input option [Unchecked: verify against current Claude Code]. A location with more exits than that needs paging or typed input.
- Game data lives in a local DB reached through scripts. No JSON or markdown files as game state anywhere in the project, because those are token eaters [Gogi].
- One setup script run after cloning the repo. It checks and installs whatever is needed [Gogi]. Docker is out, because it is too much for people who have never touched it [Gogi].
- The player needs Node.js to run their own quest code [My guess]. The setup script should check for it.
- The repo is public, so anything committed ships to every player. Quest tests and solutions are visible to anyone who opens the repo [My guess]. The owner's answer to this is the honor system: the Master catches cheating, the code does not prevent it.

## 5. The game

### 5.1 Onboarding and hero [Gogi unless marked]

1. The player starts the game in a terminal.
2. The player builds a hero from standard D&D structure: **race and class are separate picks**.
3. Custom race or custom class is allowed. The Master asks the player a few questions to fill the gaps a custom entry leaves.
4. The player names the hero.
5. Traits are point adjustments on ability scores, for example +2 initiative or -1 agility, under the standard D&D limit. The standard rule is 5e point buy: 27 points, every ability starts at 8, none above 15 before race bonuses [Unchecked, from my memory; verify before implementing].
6. The Master offers a few setting versions, each with a brief description. The player picks one and customizes it, or writes the whole setting description themselves.

### 5.2 World

- Setting varies per player: medieval, cyberpunk, Toy Story-style, Mad Max, any book or film world, and so on [Gogi].
- **Fixed for every player:** the number of locations, NPCs, and quests. The subjects are the same, so the tasks stay relatively similar [Gogi].
- **Varies:** the setting and its flavor [Gogi].
- The learning path is fixed and the setting is a skin over it: the same ladder of JS quests, dressed as a cyberpunk heist or a wasteland convoy [Gogi, confirmed].
- The Master's voice fits the vibe of the chosen world [Gogi]. There is no single Master voice. A per-setting voice framework plus a list of banned AI-speak is needed so the anti-goal can be tested [My guess].

### 5.3 Curriculum

Scope in the owner's words: the JS basics up to async, with the event loop, fetch, and timeouts. Basics include strings, arrays, objects, and similar. Proposed ladder, ordering is [My guess]:

1. Variables, strings, numbers, arrays, objects
2. Functions, conditionals, loops
3. Scope and closures
4. Callbacks, timeouts
5. Promises, async/await
6. fetch, and the event loop

One of the first quests is writing or inspecting the dice code, so the player learns the roll is as random as JS allows [Gogi].

### 5.4 Moving and talking [Gogi]

Claude's built-in choice prompts handle most turns: single or multiple choice with a custom input option. Plain text input is used in some cases. The goal is dialog that feels natural.

### 5.5 The quest loop [Gogi]

Every quest is a code task. **Quest checks are fixed in the repo and the Master only reskins the story around them** [Gogi, accepted my recommendation]. This keeps step 1 token-free, keeps difficulty under the owner's control, and rules out broken or unsolvable checks.

1. The quest names the file the player must write in.
2. The player writes the solution.
3. **Step 1: a plain script runs the file and compares the outcome.** No AI is involved [Gogi, confirmed].
   - If it fails, stop. The player sees the standard "failed, try again" screen showing what their code returned and what was requested. Honor does not change. The file is not read [Gogi].
4. **Step 2: only if step 1 passes, the Master reads the file** and checks that real code solves the real problem [Gogi, confirmed]. This is the one place judging costs tokens.
5. If the file shows cheating, such as returning the expected value without solving anything, the player loses honor/reputation [Gogi].
6. Feedback tone depends on honor, and the tone review starts only after step 1 passes [Gogi]:
   - High enough honor/reputation: a gentle code review.
   - Low honor/reputation: the game demolishes the player with swearing and heavy roasting.

### 5.6 Honor and reputation [Gogi]

Modeled on Red Dead Redemption 2.

**Goes down**
- Swearing
- Talking shit to NPCs
- Deviant behavior
- Breaking things for no reason
- Any kill, except when the player was attacked first
- Cheating in code
- Using "illegal" documentation links (minor decrease)
- Tricking the Master into leaking solution parts (minor decrease)

**Goes up**
- Kind words and generous acts
- Helping an NPC who is struggling: a guaranteed bump even if the help fails, a larger one if it succeeds
- Greeting and chatting with NPCs: an occasional minor bump
- Clean solves, especially without hints [Gogi confirmed my guess]

**Low honor effects:** NPCs avoid you. The brave few who stay near you treat you like dirt or a floormat [Gogi].

**Logging:** honor and complexity changes are logged as timestamped events, not one running number, because the end screen shows progression over time [Gogi confirmed].

**Cost:** the Master reads player input to judge conduct. This is AI work and costs tokens. Accepted [Gogi].

**Legal links** are official documentation and specifications. **Illegal links** are everything else [Gogi]. The legal list [Gogi]:
- MDN
- W3Schools
- ECMAScript language specification (tc39.es/ecma262)
- Node.js official docs (nodejs.org/docs)
- WHATWG Fetch standard (fetch.spec.whatwg.org)
- javascript.info
- Eloquent JavaScript (free online book)

The URLs for the last two and the exact domains for each source should be verified by the builder before they go into the game.

### 5.7 Combat [Gogi unless marked]

- D&D-style, not full JS.
- Per turn: the agent asks the player for input, a script rolls the dice for the NPCs, and the step is logged to the fight's log in the DB by running a script with filled params. **Every fight log goes to the DB.**
- Dice are rolled by script, not by the AI [Gogi confirmed].
- **Advanced moves trigger a random JS problem** on top of the normal D&D complications. Example: "I jump 7 feet high, do a kickflip, and shoot 3 arrows straight into each enemy's head" requires solving a hard enough JS problem. The Master generates these problems and decides how they are judged [Gogi]. A generated problem has no guarantee of being solvable or correct, so the builder should consider a script-run validation step before the problem is shown [My guess].
- Fights start when an NPC gets frustrated: a shopkeeper warns the player twice, then may start a fight if the player keeps standing behind the counter.
- Fights can sit inside a quest: beat a guy to get a manuscript holding an MDN link or a full explanation of a solution.

### 5.8 Dice integrity [Gogi]

If the player changes the dice code, they lose all reputation, drop to level 1, and start the game over on the lowest settings for their hero. A way to detect the change is needed, such as a stored fingerprint of the dice file [My guess]. The restart happens in the same world. With honor at the floor, every NPC wants to kill the hero [Gogi].

### 5.9 Stamina [Gogi]

- Stamina is the real 5hr Claude usage limit. The owner reports Claude Code already shows that limit accurately.
- It is shown in a custom bottom bar for this project only. How to wire a project-scoped bar to that number is a research item, not a decision (section 8).
- As stamina drops, moves get less sharp and intellectual abilities fade. After 60% of the limit is used, both drop noticeably. Before 60%, there is only a minor decrease after complex or hard actions.
- Mechanically, I read this as dice and ability penalties: physical tiredness hits agility-type checks, mental tiredness hits INT-type checks, separate from how hard the code quests are [My guess].
- Just before zero, the player sees: "you're completely tired. you fell on the spot where you were standing at _LOCATION_ for _HOURS_". `_HOURS_` is the time until the limit resets [My guess].

### 5.10 Ending [Gogi]

A stats page built from DB queries. It shows hours spent, enemies defeated, JS subjects learned, tasks solved, complexity progression, and honor progression over time. It is hidden deep in the project code and revealed only at the end. "Hidden" can only mean not advertised, since the repo is public and anyone can open it [My guess, Gogi confirmed]. The certificate is parked.

Decided in Plan 7 [Gogi]: the ending needs every quest solved and a final boss (a seventh NPC) beaten. The page is one static HTML file compiled by a script, not a server. Hours spent are estimated from existing timestamps. JS subjects learned was skipped for now.

## 6. Technical decisions

- **Game DB: SQLite [Gogi, final].** Chosen over embedded Postgres, PGlite, and DuckDB after a comparison. Notes from the research (blog posts and the SQLite limits page, no hard benchmarks found):
  - A SQLite file does not limit table count or relations. Joins cap at 64 tables per query and tables at 2000 columns by default. Neither matters here.
  - Foreign keys are off by default and apply per connection, so every script must turn them on.
  - There is one writer at a time. In WAL mode many readers can run alongside it. The game is single-player with sequential scripts, so this should not bite [My guess].
  - Locations graph traversal uses recursive CTEs [My knowledge]. Use `UNION` or visited tracking to avoid cycles.
  - Recommended per-connection setup from several guides: WAL, `synchronous=NORMAL`, a busy timeout, `foreign_keys=ON`.
- **Scripts only.** The agent talks to the DB through scripts. Deterministic work (running quest files, dice, fight logging, queries) is code. Only judgment work (cheating review, conduct review, dialog, world content) is AI.
- **One hero and one world per install in the MVP [Gogi].** Main tables carry a save id from day one so multiple saves can come later without a migration [My call, accepted by Gogi].
- **Install:** clone the repo, run one `.sh` file that checks and installs what is needed [Gogi].
- **Host:** Claude Code first. The choice-prompt UI is Claude-specific, so other models will need their own input layer [My guess].

## 7. Development process and tracking [Gogi unless marked]

- **Tasks:** GitHub Issues and a GitHub Projects board on https://github.com/yamnyk/_JS-dnd.git. Either the owner creates them or Claude does through the API. Claude asks before each batch, because creating issues and boards is outward-facing. Board access through `gh` may need an extra token permission [Unchecked].
- **Alternatives considered:** Linear, ClickUp, and Asana were rejected because they add an account and a subscription. GitHub is free and the code lives there.
- **Dev notes: a separate dev-only SQLite DB, gitignored.** It is separate from the game DB because the repo is public and the game DB ships to players.
- **Session start:** read the board, read the latest task status from the dev DB, and greet the owner with the current state. A SessionStart hook is the deterministic way [My guess]. A `CLAUDE.md` instruction is the softer option.
- **Session end:** write the current task's state to the dev DB. If the task is done, record exactly that it was completed. Also record predictions of possible next steps from the conversation, labeled as predictions and kept apart from confirmed status [My call].
- **Working rules that apply to the builder (from the owner's global rules):**
  - No git commands unless the owner asks.
  - No code changes unless the owner asks.
  - Ask before any outward-facing action.
  - Prefer scripts over agents for deterministic work.
  - No em-dashes or en-dashes anywhere, including code, comments, commits, and docs.
